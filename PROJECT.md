## 1. Vision

**Dating** — современное веб-приложение знакомств, разработанное полностью на Laravel.

### Цель

Создать красивый, быстрый и приятный сайт знакомств **без SPA-фреймворков** (React/Vue).
Frontend остаётся максимально простым. Максимально используются возможности Laravel и минимальный JavaScript.

### Ключевой принцип

> **Не пытаться сразу сделать аналог Tinder.**
> На каждом спринте должен получаться небольшой, но **полностью рабочий продукт**.
>
> - После Sprint 2 — уже можно смотреть анкеты.
> - После Sprint 4 — получать совпадения.
> - После Sprint 5 — общаться.
>
> Такой подход позволяет постоянно иметь рабочее приложение и значительно упрощает разработку и ревью.

## 3. Архитектура

```
Browser
  ↓
Blade
  ↓
Controllers
  ↓
Services (только при наличии бизнес-логики)
  ↓
Repositories (только при реальной необходимости)
  ↓
Eloquent
  ↓
PostgreSQL
```

### Принципы архитектуры

- **Не усложнять заранее.**
- Service Layer — только там, где появляется реальная бизнес-логика.
- Repository — **не создавать "на будущее"**. Eloquent уже является репозиторием.
- Никаких абстракций ради абстракций.

## 7. Правила разработки

### Каждая задача — отдельная ветка

```
main
  ↓
feature/sprint-01
  ↓
Pull Request
  ↓
Code Review
  ↓
Merge
  ↓
feature/sprint-02
```

### Обязательные Laravel-инструменты

- Form Requests
- Policies
- Route Model Binding
- Resource Controllers (где уместно)
- Eloquent Relationships
- Service Layer (при необходимости)

### Код

- Не писать SQL, если хватает Eloquent.
- Следовать **PSR-12**.
- Следовать **Laravel Best Practices**.
- Не дублировать код.
- Писать понятные имена методов и переменных.

## 8. Правила агента

### Перед началом работы

Агент обязан:

- Изучить существующий код.
- Понять архитектуру.
- Не ломать существующую функциональность.
- Придерживаться **Laravel Way**.
- Перечитать этот документ.

### Во время работы

- Каждый Sprint содержит **только одну законченную функциональность**.
- Не выполнять задачи из будущих Sprint.
- Не делать рефакторинг несвязанных частей проекта.
- Не менять стиль кода без необходимости.
- Не добавлять зависимости без обоснования.

### После завершения Sprint

Обязательно:

- Пройтись по всему коду.
- Удалить неиспользуемый код.
- Проверить форматирование.
- Проверить миграции.
- Проверить маршруты.
- Убедиться, что ничего не сломано.

После этого:

```
Commit
  ↓
Push
  ↓
Создать Pull Request
```

После создания PR работа заканчивается.
**Следующий Sprint начинается только после Merge.**

## 10. Definition of Done

Каждый Sprint считается завершённым **только если**:

- ✅ Функциональность полностью реализована.
- ✅ Код соответствует PSR-12 и Laravel Best Practices.
- ✅ Нет очевидного дублирования кода.
- ✅ Выполнена локальная проверка работы.
- ✅ Все изменения находятся в одной feature-ветке.
- ✅ Создан Pull Request с кратким описанием изменений.
- ✅ Агент **не приступает** к следующему Sprint до завершения ревью и слияния.

---

## 11. Итоговые принципы

1. **Laravel Way** — используем возможности фреймворка, а не изобретаем свои.
2. **Простота** — минимум JS, никаких SPA.
3. **Поэтапность** — каждый спринт даёт рабочий продукт.
4. **Качество** — красивый UI, чистый код, хорошая архитектура.
5. **Дисциплина** — один спринт = одна ветка = один PR = один merge.
6. **Не ломать** — существующий функционал всегда работает.
7. **Не усложнять** — никаких абстракций "на будущее".
